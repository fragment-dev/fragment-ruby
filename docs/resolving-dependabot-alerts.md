# Resolving Dependabot Alerts

## Overview

How to triage and resolve Dependabot security alerts in `fragment-dev/fragment-ruby`.

The thing that makes this repo different from a normal application: **it is a
published gem.** The blast radius of an alert depends on which dependency list
the vulnerable gem is reachable from.

| Where the dependency lives | Who is exposed |
| --- | --- |
| `fragment-dev.gemspec` `add_runtime_dependency` (`graphql`, `graphql-client`, `sorbet-runtime`) and anything they pull in | Every downstream app that installs `fragment-dev`. Treat as production. |
| `Gemfile` gems in `group: :development` (`rubocop`, `sorbet`, `tapioca`, `minitest`, `simplecov`, `webmock`, `rake`) | This repo's CI and contributors only. Dev tooling. |
| `Gemfile` gems with no group (`http`, `pry`, `reline`, `rexml`, `thor`, `uri`) | Only this repo — they are not gemspec dependencies, so they never reach a consumer. Test/console tooling in practice. |

A floor pin in the `Gemfile` protects **this repo's** lockfile only. It does
**not** protect anyone who installs the published gem — only `.gemspec`
constraints do that. Keep this in mind whenever you are tempted to "fix" an
alert by editing the `Gemfile`.

## Step 1: Fetch Open Alerts

```bash
# List open alerts with severity and package info
gh api repos/fragment-dev/fragment-ruby/dependabot/alerts --paginate \
  -q '.[] | select(.state == "open") | "\(.number)|\(.security_advisory.severity)|\(.dependency.package.name)|\(.security_advisory.summary)"' | sort -u

# Get patched versions and the scope Dependabot inferred for open alerts
gh api repos/fragment-dev/fragment-ruby/dependabot/alerts --paginate \
  -q '.[] | select(.state == "open") | "\(.dependency.package.name)|\(.dependency.scope)|\(.security_vulnerability.first_patched_version.identifier // "no patch")|\(.security_vulnerability.vulnerable_version_range)"' | sort -u
```

`.dependency.scope` is `runtime` or `development` as Dependabot read it from the
manifest. It is a hint, not the answer — Dependabot sees `Gemfile.lock`, so an
ungrouped `Gemfile` gem reads as `runtime` even though no consumer of the
published gem ever gets it. Confirm with Step 2.

## Step 2: Assess Impact on the Published Gem

### 2.1 Examine the Vulnerability Mechanism

Read the advisory and answer: what input triggers it, what the impact is, and
what conditions exploitation needs. Most alerts here land on parsers (`rexml`,
`uri`, `addressable`, `nokogiri`-likes) reached through HTTP or GraphQL
schema handling, so "is the input attacker-controlled?" is usually the
deciding question.

### 2.2 Trace Gem Usage

Bundler has no `yarn why`. Use the lockfile directly — this prints every spec
that depends on the gem, with the constraint each one asks for:

```bash
rdeps() {
  ruby -rbundler -e '
    lock = Bundler::LockfileParser.new(File.read("Gemfile.lock"))
    target = ARGV[0]
    lock.specs.each do |s|
      s.dependencies.each do |d|
        puts "#{s.name} (#{s.version}) -> #{d.name} #{d.requirement}" if d.name == target
      end
    end
  ' "$1"
  echo "--- direct in Gemfile/gemspec? ---"
  grep -nE "['\"]$1['\"]" Gemfile fragment-dev.gemspec
}

rdeps rexml
```

Walk up the tree the same way until you reach either `fragment-dev` (the PATH
spec at the top of `Gemfile.lock` — i.e. a gemspec runtime dependency, so
consumers are exposed) or a `Gemfile` entry (this repo only).

`bundle info <gem>` gives the resolved version and install path;
`bundle exec ruby -e 'puts $LOADED_FEATURES.grep(/<gem>/)'` after loading the
SDK tells you whether it is actually loaded at runtime rather than merely
installed.

Then check whether the vulnerable API is called at all:

```bash
rg -n 'REXML|Addressable|URI\.' lib/
```

### 2.3 Determine if Dismissal is Appropriate

An alert can often be dismissed if:

1. **Dev/build tooling only** — the gem is reachable only from a
   `group: :development` gem (RuboCop, Sorbet, Tapioca, SimpleCov, WebMock) or
   from `pry`/`reline`. Never shipped, never run against untrusted input.
2. **Not reachable from the gemspec** — the gem is in the `Gemfile` but not in
   `fragment-dev.gemspec`'s dependency closure, so no consumer of the published
   gem installs it.
3. **No exploitable code path** — `lib/` never calls the vulnerable API. Note
   that "we don't call it" is weaker for gemspec runtime deps, where a consumer
   might; scope that reasoning to code we control.
4. **Input not attacker-controlled** — e.g. the GraphQL schema in
   `lib/fragment.schema.json` and `lib/queries.graphql` are checked in and
   generated by `rake graphql:update_schema` from Fragment's own API, not from
   caller input.
5. **No patch available** and the risk is acceptable given the usage above.

Do **not** dismiss on "we don't call it" alone when the gem is in the gemspec
closure. Consumers use this SDK in ways we cannot see.

## Step 3: Dismiss Alerts When Appropriate

**IMPORTANT: Always ask for permission before dismissing any alert.** Present
the analysis and the recommendation, then wait for explicit approval.

```bash
gh api -X PATCH repos/fragment-dev/fragment-ruby/dependabot/alerts/<alert-number> \
  -f state=dismissed \
  -f dismissed_reason=tolerable_risk \
  -f dismissed_comment="<detailed explanation>"
```

GitHub caps dismissal comments at 280 characters. Say where the gem sits, why
it is not a risk, and the patch status:

```bash
gh api -X PATCH repos/fragment-dev/fragment-ruby/dependabot/alerts/42 \
  -f state=dismissed \
  -f dismissed_reason=tolerable_risk \
  -f dismissed_comment="Dev tooling only: reachable via tapioca/sorbet in group :development. Not a fragment-dev.gemspec runtime dep, so no consumer of the published gem installs it. lib/ never calls the vulnerable API."
```

## Step 4: Update Gems with Available Patches

### 4.1 See What Is Already Pinned

`Gemfile` already carries floor pins that exist only to keep past alerts closed
(`rexml >= 3.4.2`, `thor >= 1.4.0`, `uri >= 1.0.4`). They are transitive
dependencies listed directly so Bundler cannot resolve back below the patch.
Check whether the gem you are fixing is already one of these:

```bash
grep -nE "['\"]<gem-name>['\"]" Gemfile fragment-dev.gemspec
```

### 4.2 Check Available Versions

```bash
gem list -r -a -e <gem-name>          # all published versions
gem specification -r <gem-name> -v <version> required_ruby_version
```

The second command matters: `fragment-dev.gemspec` declares
`required_ruby_version >= 3.2` and CI runs the 3.2/3.3/3.4 matrix. A patched
version that requires Ruby >= 3.3 cannot be adopted as a floor without dropping
a supported Ruby, which is a release decision, not an alert fix.

### 4.3 Apply the Fix

**Goal: keep the pin as close to the real dependency as possible, and only pin
what the alert requires.** Bundler has no `resolutions` block — the equivalent
is naming the transitive gem in the `Gemfile` with a floor constraint.

#### Option A: Bump the parent (preferred)

If a newer version of the depending gem already requires the patched version,
raise the parent instead of pinning the child. One constraint, and it goes away
on its own later:

```bash
gem specification -r <parent> -v <new-version> dependencies
bundle update <parent> --conservative
```

#### Option B: Floor-pin the transitive gem in `Gemfile` (repo-only fix)

When the parent has not released a fix, add the gem to `Gemfile` with a `>=`
floor, matching the existing style:

```ruby
gem 'rexml', '>= 3.4.2'
```

Use `>=`, not `~>` or `=`: a floor closes the alert without freezing the gem
against future patches, and it keeps the resolver free.

This fixes CI and contributors. It does **not** fix consumers of the published
gem.

#### Option C: Constrain in `fragment-dev.gemspec` (affects consumers)

Only when the vulnerable gem is reachable from a gemspec runtime dependency and
downstream apps are genuinely exposed. Prefer raising the existing runtime
dependency's floor:

```ruby
s.add_runtime_dependency 'graphql', '>= 2.2.5', '< 3.0'
```

Adding a brand-new `add_runtime_dependency` purely to pin a transitive gem
imposes that constraint on every downstream app and can conflict with their
own resolution — do it only when the exposure is real, and call it out
explicitly in the PR. A gemspec change is a public API change: it needs a
`CHANGELOG.md` entry and a version bump in `lib/fragment_client/version.rb`.

### 4.4 Update the Lockfile

Conservatively, so one alert fix does not turn into a repo-wide dependency bump:

```bash
bundle update <gem-name> --conservative
git diff --stat Gemfile.lock   # confirm only the expected specs moved
```

Use plain `bundle install` after editing `Gemfile` only if the constraint is
already satisfiable without moving anything else.

### 4.5 Regenerate the Sorbet gem RBIs

**Do not skip this.** `sorbet/rbi/gems/` holds one checked-in RBI per resolved
gem, named by version (`activesupport@8.1.3.rbi`). Any lockfile change makes
that directory stale and `srb tc` will fail in CI's Quality job.

```bash
bundle exec tapioca gem            # syncs: adds, removes, renames to match the lockfile
git status sorbet/rbi/gems
```

If the bump touches `graphql` or `graphql-client`, also check whether the
generated DSL RBIs and the typed-entry snapshot moved:

```bash
bundle exec rake snapshot
git diff --stat -- sorbet/snapshots
```

A snapshot diff means the surface callers touch changed — that is a reviewed
decision, not a chore. Explain it in the PR or reconsider the bump.

### 4.6 Verify

Run what CI runs:

```bash
bundle exec rake test
bundle exec srb tc
bundle exec rubocop
bundle exec rake graphql:update_schema && git diff --exit-code   # only if graphql moved
```

Across the support matrix when the bump is anywhere near the Ruby floor — CI
covers 3.2, 3.3 and 3.4, and `.ruby-version` is 3.3.6, so a 3.2 break will not
show up locally.

If a check fails: read the gem's CHANGELOG, look for an intermediate version
carrying the security fix without the breaking change, and if none exists, say
so in the PR rather than working around it in `lib/`.

## Step 5: Create the PR

```bash
git add Gemfile Gemfile.lock fragment-dev.gemspec sorbet/rbi
git commit -m "Fix Dependabot security alerts for <gems>"
```

The PR should state:

- Which gems moved and to what versions
- Whether the fix reaches consumers of the published gem (gemspec) or only this
  repo (Gemfile), and why that is the right scope
- Which alerts were dismissed and why
- Whether `sorbet/rbi/gems` or `sorbet/snapshots` changed, and why
- Any alert intentionally left open, with the reason

## Common Scenarios

### The vulnerable gem is only reachable through dev tooling

Sorbet, Tapioca, RuboCop and their transitive dependencies pull in a large tree
that never ships. Trace with the `rdeps` helper, confirm no path reaches
`fragment-dev` in the lockfile's PATH section, and dismiss as `tolerable_risk`
naming the tooling path.

### The patched version raises the Ruby floor

`fragment-dev.gemspec` says `>= 3.2` and CI proves it on 3.2. If the patch
requires 3.3+, do not adopt it as a floor pin — that silently drops a supported
Ruby for every consumer. Dismiss with the Ruby-floor reason, or open a separate
issue proposing the support-matrix change.

### No patch available

Check whether the parent gem has dropped or replaced the dependency in a newer
version. If not, assess exploitability using Step 2, and dismiss with the usage
context if the risk is acceptable. If it is not acceptable and the gem is in the
gemspec closure, that is a real problem — escalate rather than pin around it.

### Updating one gem cascades through the lockfile

`bundle update <gem>` without `--conservative` will happily move dozens of
specs, which then churns all of `sorbet/rbi/gems`. Always start conservative;
if the resolver genuinely needs the wider bump, do it deliberately and say so in
the PR.

### The alert is on the vendored `.gem` artifact

`fragment-dev-1.3.0.gem` is a checked-in build artifact, not part of the
dependency graph. Alerts do not come from it, and nothing in it needs updating
to close one.
